develop 브랜치 기준으로 현재까지 변경된 코드를 켄트 백(Kent Beck) 스타일로 리팩토링해주세요.

## 단계

1. **변경사항 파악**
   - `git fetch origin` 으로 최신 develop 정보 동기화
   - `git log --oneline origin/develop..HEAD` 로 작업한 커밋 확인 (develop이 없으면 main 사용)
   - `git diff origin/develop...HEAD` 로 전체 변경사항 확인
   - 변경된 파일 목록과 핵심 변경 의도를 한 줄로 요약

2. **켄트 백 원칙 기반 리팩토링 진단**
   다음 원칙으로 변경된 코드를 점검:
   - **Tidy First**: 구조 변경(refactoring)과 동작 변경(behavior change)이 한 커밋에 섞여있지 않은지
   - **Small Steps**: 한 번에 너무 많은 일을 하는 함수/메서드가 있는지
   - **Make the change easy, then make the easy change**: 변경을 어렵게 만든 결합도/중복이 있는지
   - **명확한 의도 표현**: 변수/함수 이름이 의도를 드러내는지 (Reveals Intent)
   - **중복 제거(DRY)**: 추출 가능한 중복 로직이 있는지
   - **작은 함수**: SRP를 어기는 큰 함수가 있는지
   - **테스트 가능성**: 부수효과나 의존성으로 테스트하기 어렵게 만든 부분이 있는지

3. **리팩토링 적용**
   - 가장 임팩트가 큰 항목부터 적용
   - 구조 변경만 수행하고 **동작은 절대 바꾸지 않음**
   - 기존 테스트가 있다면 통과 상태 유지
   - 큰 리팩토링은 작은 스텝으로 나눠서 진행

4. **결과 정리**
   - 어떤 원칙에 의해 무엇을 바꿨는지 항목별로 요약
   - 위험 신호(테스트 없음, 큰 변경 등)가 있다면 명시
   - 사용자가 확인할 수 있도록 변경된 파일/함수 목록 제시

## 주의사항

- 동작을 바꾸는 변경(버그 픽스 등)은 하지 말 것. 순수 리팩토링만 수행
- 과도한 추상화 금지. 3번 이상 반복되는 경우에만 추출
- 사용자가 의도적으로 작성한 코드 스타일은 존중
- 한 번에 너무 많이 바꾸지 말고, 변경 묶음 단위로 설명
- 커밋/푸시는 하지 않음. 변경만 적용하고 사용자에게 검토 요청

develop 브랜치 기준으로 현재 커밋까지 변경된 코드에 엣지 케이스 누락이나 로직 오류가 없는지 꼼꼼히 점검해주세요.

## 단계

1. **변경사항 파악**
   - `git fetch origin` 으로 최신 develop 정보 동기화
   - `git log --oneline origin/develop..HEAD` 로 작업한 커밋 확인 (develop이 없으면 main 사용)
   - `git diff origin/develop...HEAD` 로 전체 변경사항 확인
   - 변경된 파일 목록과 핵심 변경 의도를 한 줄로 요약

2. **점검 범위 한정**
   - 분석 대상은 **이번 diff에서 추가/수정된 코드**로 한정 (기존 코드는 변경된 라인이 영향을 줄 때만)
   - 변경된 함수가 호출하는 의존성/호출처도 필요한 만큼만 읽어 컨텍스트 확보
   - 큰 diff면 파일/관심사 단위로 나눠 병렬 점검(Task) 활용 가능

3. **로직 오류 점검**
   - **조건문**: 비교 연산자 방향(<, <=, >, >=), 경계값, 부정 조건, early return 누락
   - **불리언/단축평가**: `&&`/`||` 우선순위, truthy/falsy 함정(0, "", NaN, false)
   - **상태 갱신**: 누락된 setState, stale closure, 의존성 배열 누락/과다(useEffect/useMemo/useCallback)
   - **비동기**: await 누락, race condition, 에러 전파, Promise 미처리
   - **분기 누락**: switch/if-else 에서 처리 안 된 케이스, 기본값 부재
   - **타입 계약**: 함수 입출력 타입이 실제 사용과 일치하는지, 좁히기(narrowing) 빠진 곳

4. **엣지 케이스 점검**
   - **빈 값/경계**: null, undefined, 빈 배열/문자열, 0, 음수, 최대/최소값
   - **숫자**: 정수/실수 변환, 반올림, 0 나눗셈, 오버플로우, 단위 불일치(원/만원 등)
   - **배열/객체**: 인덱스 범위 초과, 빈 컬렉션 map/reduce, 키 부재, 얕은/깊은 복사
   - **사용자 입력**: 미입력, 최대 길이, 특수문자, 음수/과다 입력
   - **인증/권한**: 로그인 전후 분기, 만료, 권한 게이팅 누락
   - **UI 상태**: 로딩/에러/빈 상태(empty) 미처리, 중복 클릭, 비활성 조건

5. **부수효과/silent failure 점검**
   - 삼켜진 에러(빈 catch, 무시된 reject), 잘못된 fallback(에러를 정상값으로 둔갑)
   - toast/무효화/리페치 등 side effect 누락 (특히 server action -> mutate 전환부)
   - 로깅/추적 이벤트가 의도대로 발생하는지

6. **프로젝트 규칙 위반 점검** (CLAUDE.md / 메모리 기준)
   - 해당하는 경우 tRPC 무효화 헬퍼, queryOptions 패턴, 인증 게이팅(useCurrentUserInfo), ASCII 연산자 등 프로젝트 컨벤션 위반 여부

7. **결과 정리**
   각 발견 항목을 심각도별로 정리:
   - **🔴 Critical**: 실제 버그/데이터 손상/크래시 가능성 — 위치(`file:line`), 재현 시나리오, 수정 방향
   - **🟡 Warning**: 엣지 케이스 누락/잠재 위험 — 어떤 입력에서 문제되는지
   - **🔵 Info**: 사소한 개선 여지/확인 권장 사항
   - 발견 항목이 없으면 "점검 완료, 발견된 문제 없음"을 근거(점검한 범위)와 함께 명시

## 주의사항

- **코드를 직접 수정하지 말 것.** 분석과 보고만 수행. (수정은 사용자가 별도 요청)
- 추측을 단정하지 말 것. 확신이 낮은 항목은 "확인 필요"로 표시하고 근거를 함께 제시
- 오탐(false positive)을 줄이기 위해, 의심 항목은 실제 호출처/데이터 흐름을 확인한 뒤 보고
- 위치는 항상 `file:line` 형식(클릭 가능)으로 제시
- 스타일/포맷팅 지적은 최소화. 동작·정확성에 집중 (리팩토링은 /refactor 사용)
- develop 기준 diff가 비어있으면 그 사실을 알리고 대상 브랜치를 사용자에게 확인

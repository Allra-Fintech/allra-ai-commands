현재 변경사항을 전체적으로 점검한 뒤 커밋하고 푸쉬해주세요.

인자: $ARGUMENTS

`--yes` 가 포함되어 있으면 4단계의 푸쉬 확인을 생략하고 바로 진행합니다. 그 외 인자는 무시합니다.

## 단계

1. **현재 상태 파악**
   - `git status` 로 변경 파일 확인
   - `git diff` 로 unstaged 변경사항 확인
   - `git diff --staged` 로 staged 변경사항 확인
   - `git log -5 --oneline` 로 최근 커밋 스타일 확인 (메시지 컨벤션 학습)
   - `git branch --show-current` 로 현재 브랜치 확인

2. **전체 점검**
   다음 항목을 빠르게 체크:
   - **의도 일관성**: 변경된 파일들이 한 가지 작업 단위에 부합하는지
   - **잔여물**: `console.log`, `print` 디버그 코드, 주석처리된 코드, TODO 임시 메모가 남아있지 않은지
   - **민감정보**: `.env`, API 키, 비밀번호, 토큰 같은 게 포함되어 있지 않은지
   - **불필요한 파일**: `.DS_Store`, `node_modules`, 빌드 산출물 등이 들어가지 않았는지
   - **테스트/타입체크**: 프로젝트에 lint/test/typecheck 스크립트가 있다면 빠르게 실행 (있을 때만)
   - **커밋 단위 적정성**: 너무 많은 변경이 한 커밋에 묶이지 않았는지

3. **이슈가 발견되면**
   - 사용자에게 발견된 문제를 알리고 진행 여부 확인
   - 민감정보가 있다면 절대 커밋하지 말고 즉시 중단

4. **커밋 & 푸쉬**
   - 최근 커밋 스타일에 맞춰 메시지 작성 (Conventional Commits 또는 프로젝트 컨벤션)
   - 메시지는 한국어/영어 중 기존 커밋 패턴을 따름
   - "왜(why)" 중심으로 1-2줄 작성
   - 관련 파일만 staging (`git add -A` 대신 명시적으로)
   - 커밋까지는 로컬 작업이므로 바로 진행

   **푸쉬 전 확인 (필수)**

   커밋 후, 푸쉬하기 전에 아래 내용을 그대로 보여주고 AskUserQuestion으로 승인받습니다.
   `--yes` 인자가 있으면 이 확인을 생략합니다.

   ```
   ## 푸쉬 전 확인

   대상: origin/<branch>  (업스트림 <있음: 기존 추적 브랜치 | 없음: -u 로 새로 생성>)

   커밋 내역:
   <git log @{u}..HEAD --oneline 결과. 업스트림 없으면 origin/develop..HEAD 기준>

   커밋 메시지 전문:
   <이번에 작성한 커밋 메시지 전체>

   경고:
   - <보호 브랜치 여부 / 민감정보·디버그 잔여물 탐지 결과 / 그 외 2단계에서 발견된 사항. 없으면 "없음">
   ```

   선택지: `푸쉬` / `커밋 메시지 수정` / `중단`
   - **푸쉬**: `git push` 실행. 업스트림이 없으면 `git push -u origin <branch>`
   - **커밋 메시지 수정**: `git commit --amend` 로 고치고 다시 이 확인으로 돌아옴
   - **중단**: 커밋은 로컬에 남겨두고 종료. 사용자에게 `git reset --soft HEAD~1` 로 되돌릴 수 있음을 안내

5. **결과 보고**
   - 커밋 SHA와 메시지
   - 푸쉬된 원격 브랜치
   - PR 링크가 있다면 함께 표시

## 주의사항

- 민감정보 발견 시 즉시 중단하고 사용자에게 보고
- `--no-verify`, `--force` 같은 위험 옵션은 사용자가 명시적으로 요청하지 않는 한 사용 금지
- **승인 없이 푸쉬 금지.** 4단계의 푸쉬 전 확인을 건너뛰는 경우는 `--yes` 인자가 있을 때뿐
- main/master/develop 같은 보호 브랜치인 경우, `--yes` 가 있어도 확인을 생략하지 않음
- 빈 커밋 만들지 말 것
- 점검 단계에서 발견된 사소한 문제는 사용자에게 알리되, 막지는 말 것 (판단은 사용자에게)
